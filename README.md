# PostgreSQL Query Performance & Optimizer Analyzer

This is a PostgreSQL analysis project focused on **indexing, predicate selectivity, execution plans, and cost-based query optimization** using TPC-H workloads.

The project brings together a series of experiments that investigate not only **how query performance changes**, but also **why PostgreSQL chooses a particular execution plan, when that plan changes, and whether the optimizer's decisions align with observed execution performance**.

---

## Overview

Modern database systems rely on indexes and cost-based query optimizers to execute queries efficiently. However, the most appropriate execution strategy can depend on several factors, including:

* Predicate selectivity
* Available indexes
* Data organization
* Query parameters
* Optimizer cost estimates
* Physical access methods

This project experimentally studies these factors using **PostgreSQL** and **TPC-H workloads**.

The analysis is organized into two main areas:

### 1. Indexing Analysis

Experiments investigating:

* Index construction time
* The relationship between predicate selectivity and execution time
* Different PostgreSQL access-method configurations
* Candidate indexes for TPC-H Query 6

### 2. Query Optimizer Analysis

Experiments investigating:

* Structural equivalence of PostgreSQL execution plans
* Detection of optimizer plan switches
* Runtime behavior around plan switches
* Classification of optimizer switches as **early, delayed, or correct**
* Identification of empirically observed switch points when the optimizer's decision differs from measured runtime behavior

---

## Project Goals

The primary goals of this project are to:

1. Understand how indexes influence PostgreSQL query execution.
2. Study the relationship between **predicate selectivity** and execution time.
3. Analyze the physical execution plans generated by PostgreSQL.
4. Detect when the optimizer changes execution plans as query parameters vary.
5. Compare optimizer-selected plans against their **measured execution performance**.
6. Investigate cases where the optimizer's plan-switch point differs from the empirically observed runtime crossover.

# Experiments

## Indexing Analysis

### Index Build Timing

This experiment compares two approaches to index creation:

* Creating an index **before** inserting the data.
* Inserting the data first and creating the index **afterward**.

The experiment measures the time required in each case and examines how the timing of index construction affects the overall data-loading process.

**Location:**

```text
indexing-analysis/01-index-build-timing/
```

---

### Selectivity Benchmark

This experiment studies how query execution time changes as the **selectivity of a range predicate** varies.

The benchmark first determines query parameters corresponding to target selectivity levels and then evaluates query execution across a range of selectivities.

The following configurations are considered:

* No index
* Index on the predicate column
* Sequential scans disabled
* Clustered index
* Index-only access

PostgreSQL execution plans are collected using JSON-formatted `EXPLAIN` output, allowing the selected physical operators to be analyzed alongside measured execution time.

**Location:**

```text
indexing-analysis/02-selectivity-benchmark/
```

---

### TPC-H Query 6 Index Analysis

This experiment analyzes **TPC-H Query 6** to identify relevant search keys and candidate indexes.

The query predicates and execution behavior are examined to determine which columns are suitable for indexing and how the resulting access methods affect query execution.

**Location:**

```text
indexing-analysis/03-query6-index-analysis/
```

# Query Optimizer Analysis

## Plan Equivalence

PostgreSQL's `EXPLAIN` output provides a detailed representation of the physical execution plan selected by the optimizer.

This component converts JSON execution plans into a representation of their **physical operator structure** and determines whether two plans are structurally equivalent.

The comparison focuses on the execution strategy itself rather than:

* Query parameter values
* Estimated costs
* Estimated cardinalities

This provides a basis for detecting meaningful changes in the optimizer's selected execution strategy.

**Location:**

```text
optimizer-analysis/01-plan-equivalence/
```

---

## Plan Switch Detection

For parameterized queries, PostgreSQL may select different execution plans as query parameters change.

This experiment detects such **plan switches** by comparing execution plans for neighboring parameter values and identifying points where the physical plans are no longer equivalent.

The search is designed to efficiently explore the parameter space under the monotonicity assumptions defined for the experiment.

**Location:**

```text
optimizer-analysis/02-plan-switch-detection/
```

---

## Switch Performance Analysis

Detecting a plan switch does not necessarily tell us whether the optimizer switched at the most appropriate point.

The optimizer selects a plan based on its cost estimates, while actual execution time depends on the behavior of the query at runtime.

For each detected switch, the experiment measures the following combinations:

```text
RT(Pi, qi)
RT(Pj, qj)
RT(Pi, qj)
RT(Pj, qi)
```

where `Pi` and `Pj` represent the two candidate execution plans and `qi` and `qj` represent query instances on either side of the optimizer's switch point.

Alternative plans are explicitly forced using the PostgreSQL `pg_hint_plan` extension.

The measured runtimes are then used to classify the optimizer's switch as:

* **EARLY**
* **DELAYED**
* **CORRECT**

**Location:**

```text
optimizer-analysis/03-switch-performance-analysis/
```

---

## Optimal Switch Point

For switches classified as **EARLY** or **DELAYED**, this component investigates where the actual runtime crossover occurs.

The objective is to determine an **empirically observed switch point** based on measured execution times and validate it using the relevant plan/query combinations.

This allows the optimizer's selected switch point to be compared against the point at which the alternative execution plan becomes faster in practice.

**Location:**

```text
optimizer-analysis/04-optimal-switch-point/
```

# Methodology

The project follows an experimental workflow:

```text
                 TPC-H Data
                     │
                     ▼
                SQL Workload
                     │
                     ▼
          ┌─────────────────────┐
          │ PostgreSQL Optimizer│
          └─────────────────────┘
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
   Execution Plan          Query Execution
          │                     │
          ▼                     ▼
 Plan Structure            Runtime Data
          │                     │
          └──────────┬──────────┘
                     ▼
              Analysis & Comparison
                     │
          ┌──────────┼───────────┐
          ▼          ▼           ▼
      Indexing    Plan Switches  Optimizer
      Behavior    & Equivalence  vs Runtime
```

For optimizer experiments, the analysis separates four questions:

1. **What execution plan does PostgreSQL choose?**
2. **At what parameter value does the optimizer switch plans?**
3. **How do the candidate plans perform when actually executed?**
4. **Does the optimizer's switch point correspond to the observed runtime crossover?**

This approach makes it possible to study query optimization empirically rather than treating the optimizer as a black box.

# Reproducibility

The experiments are designed to run against a PostgreSQL installation containing the required **TPC-H dataset**.

Before running the experiments, ensure that:

* PostgreSQL is installed and accessible.
* The required TPC-H tables have been created and populated.
* The database configuration is appropriate for benchmarking.
* `pg_hint_plan` is installed for experiments that require plan forcing.
* The required Python dependencies are installed.

Experiment-specific setup and execution instructions are provided within the corresponding directories.

> **Note:** The TPC-H dataset is not included in this repository.

Excluding the dataset keeps the repository lightweight while allowing the experiments to be reproduced using the same workload.
